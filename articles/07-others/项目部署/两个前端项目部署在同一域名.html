两个前端项目部署在同一域名 ​

1.nginx 配置 ​

在 Nginx 中，若要在同一个域名下部署两个前端项目，并通过 /a 和 /b 路径来区分访问不同项目的打包文件，可以通过使用 location 指令和 alias 配置来实现。

假设：

  • 项目 A 的打包文件存放在 /path/to/project-a/dist 目录。
  • 项目 B 的打包文件存放在 /path/to/project-b/dist 目录。

配置示例： ​

yaml
server {
    listen 80;
    server_name yourdomain.com;

    # 项目 A 配置
    location /a/ {
        alias /path/to/project-a/dist/;
        index index.html;
        try_files $uri $uri/ /a/index.html;  # 如果找不到文件，回退到 index.html
    }

    # 项目 B 配置
    location /b/ {
        alias /path/to/project-b/dist/;
        index index.html;
        try_files $uri $uri/ /b/index.html;  # 如果找不到文件，回退到 index.html
    }

    # 可选：日志配置
    access_log /var/log/nginx/access.log;
    error_log /var/log/nginx/error.log;
}

配置解释： ​

  1. 项目 A 配置：
    • location /a/ {}：当请求路径以 /a/ 开头时，将会匹配到这个位置块。
    • alias /path/to/project-a/dist/;：将 /a/ 路径映射到实际的文件路径，即项目 A 的打包文件目录。
    • index index.html;：指定默认的首页文件是 index.html。
    • try_files $uri $uri/ /a/index.html;：首先尝试访问请求的路径（例如 /a/somefile.js），如果文件不存在，则回退到 /a/index.html，这通常是单页面应用（SPA）中处理路由的做法。
  2. 项目 B 配置：
    • location /b/ {}：当请求路径以 /b/ 开头时，将会匹配到这个位置块。
    • alias /path/to/project-b/dist/;：将 /b/ 路径映射到实际的文件路径，即项目 B 的打包文件目录。
    • index index.html;：指定默认的首页文件是 index.html。
    • try_files $uri $uri/ /b/index.html;：同样地，首先尝试访问请求的路径（例如 /b/somefile.js），如果文件不存在，则回退到 /b/index.html。
  3. 日志配置（可选）：添加 access_log 和 error_log，帮助记录访问日志和错误日志，便于后续的调试和性能监控。

注意事项： ​

  • 确保 /path/to/project-a/dist/ 和 /path/to/project-b/dist/ 的路径是正确的，指向各自项目的打包目录。
  • 如果你使用的是 SPA（单页面应用），try_files 可以确保当用户刷新页面时，不会返回 404 错误，而是回退到对应项目的 index.html，由前端路由进行处理。
  • 通过 alias 指令，你可以将请求的 URL 路径 /a/ 或 /b/ 映射到实际的文件系统路径，避免了 URL 和文件路径直接绑定的问题。

这样，当用户访问：

  • yourdomain.com/a/ 时，会访问项目 A 的文件；
  • yourdomain.com/b/ 时，会访问项目 B 的文件。

实例： ​

yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: ${APP_NAME}-nginx-config
  namespace: ${METADATA_NAMESPACE}
data:
  nginx.conf: |
    server_names_hash_bucket_size 256; # 增加server_name最大长度

    upstream ipaasWikiServe {
      server doc-wiki-server.${METADATA_NAMESPACE};
    }

    upstream ipaasGateway {
      server admin-gateway.${METADATA_NAMESPACE};
    }


    include domains/*;
    log_format api_log escape=json '$remote_addr - $remote_user [$time_local] "$request" '
                                    '$status $body_bytes_sent "$http_referer" '
                                    '"$http_user_agent" "$http_x_forwarded_for" "$request_body"';

    server {
      listen       80 default_server;
      listen       [::]:80 default_server;
      server_name  ${HOST};
      client_max_body_size 100m;

      add_header Cache-Control no-cache;

      include /etc/nginx/default.d/*.conf;

      proxy_set_header Cookie $http_cookie;
      proxy_set_header X-Forwarded-Host $host;
      proxy_set_header X-Forwarded-Server $host;
      proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;

      add_header 'Access-Control-Allow-Origin' '*';
      add_header 'Access-Control-Allow-Credentials' 'true';
      add_header 'Access-Control-Allow-Headers' 'DNT,X-Mx-ReqToken,Keep-Alive,User-Agent,X-Requested-With,If-Modified-Since,Cache-Control,Content-Type,Authorization';
      add_header 'Access-Control-Allow-Methods' 'GET,POST,OPTIONS';

      if ($request_method = 'OPTIONS') {
        return 204;
      }


      # 前台路径配置
      location = / {
        return 301 /wiki-backend;
      }

      location /wiki {
        alias /frontend-dist;
        index index.html index.nginx-debian.html;
        try_files $uri $uri/ /wiki/index.html;
      }

      location /wiki-backend {
        alias /backend-dist;
        index index.html index.nginx-debian.html;
        try_files $uri $uri/ /wiki-backend/index.html;
      }

      location /gateway {
        access_log /var/log/nginx/api.access.log api_log;
        rewrite ^.+gateway/?(.*)$ /$1 break;
        proxy_pass http://ipaasGateway;
      }

      # 前台 API 路径配置 (反向代理到后端服务)
      location /zyplayer-doc {
        access_log /var/log/nginx/api.access.log api_log;
        rewrite ^/zyplayer-doc/?(.*)$ /$1 break;
        proxy_pass http://ipaasWikiServe;
      }

      # 后台 API 路径配置 (反向代理到后端服务)
      location /wiki-backend-api {
        access_log /var/log/nginx/api.access.log api_log;
        proxy_pass http://ipaasWikiServe;
      }


      # 统计路径配置 (空响应)
      location /statistics {
        access_log /var/log/nginx/front-monitor.access.log api_log;
        empty_gif;
        error_page 405 =200 $request_uri;
      }
    }

2.k8 Jenkinsfile 配置 ​

核心思想，一个镜像内包含两个前端项目的打包文件 dist;

js
pipeline {
  environment {
    // Harbor地址后应用镜像的路径
    HARBOR_ADDRESS = "harbor.admin.com"
    // 命名空间
    METADATA_NAMESPACE = 'admin-common-dev'
    // ingress配置的域名
    HOST = "devwiki.admin.com"
    // Harbor地址后应用镜像的路径
    APP_PATH = "admincommon"
    // 环境名称
    ENV_NAME = "dev"
    APP_NAME = "wiki-root-front"
    // 后端服务
    APP_NAME_SERVICE = "doc-wiki-server"

    // GIT地址
    GIT_URL = 'http://10.99.186.14/baseplatform-product/wiki/wiki-root-front.git'

    // CPU资源限制
    LIMIT_CPU = '1000m'
    // 内存资源限制
    LIMIT_MEMORY = '2000Mi'

    // 镜像地址，不包含TAG/版本号
    IMAGE_PATH = "${HARBOR_ADDRESS}/${APP_PATH}/${APP_NAME}"
    // 完整镜像地址，非生产注意修改SNAPSHOT后对应的环境名
    FULL_IMAGE = "${IMAGE_PATH}:SNAPSHOT-${ENV_NAME}-${env.BUILD_NUMBER}"
  }
  agent {
    kubernetes {
      inheritFrom 'nodejs base'
      containerTemplate {
        name 'nodejs'
        image "harbor.admin.com/common/node:14.19.0"
      }
    }
  }
  stages {
    stage('CheckOut SCM') {
      steps {
        git(url: "${GIT_URL}", credentialsId: 'gitlab-cicd', branch: "${BRANCH}", changelog: true, poll: false)
      }
    }

    stage('Build dist') {
    agent none
    steps {
      container('nodejs') {
          sh 'npm config set registry http://10.99.180.187:8081/repository/npm-group/'
          // 构建项目B
          dir('wiki-backend-front') {
              sh '''npm install pnpm@7.33.1 -g
              pnpm install --ignore-scripts
              pnpm run build
              echo "Dist directory path: $(pwd)/dist"
              '''

          }
           // 构建项目A
          dir('wiki-frontend-front') {
            sh '''npm install
              npm run build
              echo "Dist directory path: $(pwd)/dist"
              '''

          }
      }
    }
  }

    stage('Build Docker and Push Combined Image') {
      agent none
      steps {
        container('base') {
          withCredentials([usernamePassword(credentialsId: 'harbor-admin', passwordVariable: 'DOCKER_PASSWORD', usernameVariable: 'DOCKER_USERNAME')]) {
            sh '''#!/bin/bash
              # 登录Harbor
              echo "$DOCKER_PASSWORD" | docker login ${HARBOR_ADDRESS} -u "$DOCKER_USERNAME" --password-stdin

              # Jenkins 工作目录
              JENKINS_DIR=${WORKSPACE}
              echo "jenkins workspace: ${JENKINS_DIR}"

              # 定义构建目录
              COMBINED_DIR="combined_build"
              if [ -d "${COMBINED_DIR}" ]; then
                rm -rf "${COMBINED_DIR}"
              fi
              mkdir -p "${COMBINED_DIR}"
              echo "combined workspace: ${COMBINED_DIR}"

              # 复制项目A的dist目录
              if [ -d "${JENKINS_DIR}/wiki-frontend-front/dist" ]; then
                cp -r "${JENKINS_DIR}/wiki-frontend-front/dist" "${COMBINED_DIR}/frontend-dist"
              else
                echo "Error: Frontend dist directory not found in ${JENKINS_DIR}/wiki-frontend-front/dist"
                exit 1
              fi

              # 复制项目B的dist目录
              if [ -d "${JENKINS_DIR}/wiki-backend-front/dist" ]; then
                cp -r "${JENKINS_DIR}/wiki-backend-front/dist" "${COMBINED_DIR}/backend-dist"
              else
                echo "Error: Backend dist directory not found in ${JENKINS_DIR}/wiki-backend-front/dist"
                exit 1
              fi

              # 复制 Dockerfile 到构建目录
              if [ -f "${JENKINS_DIR}/Dockerfile" ]; then
                cp "${JENKINS_DIR}/Dockerfile" "${COMBINED_DIR}/"
              else
                echo "Error: Dockerfile not found in ${JENKINS_DIR}"
                exit 1
              fi

              # 打印构建目录内容
              cd "${COMBINED_DIR}"
              echo "Current directory contents:"
              pwd
              ls -l

              # 构建 Docker 镜像
              IMAGE=${FULL_IMAGE}
              echo "building image: ${IMAGE}"
              # docker build -t "${IMAGE}" .
              docker build --build-arg HARBOR_ADDRESS=${HARBOR_ADDRESS} -t ${IMAGE} .

              # 推送镜像
              echo "pushing image: ${IMAGE}"
              docker push "${IMAGE}"
            '''
          }
        }
      }
    }

    stage('Deploy to DEV') {
    agent none
      steps {
        container('base') {
          withCredentials([kubeconfigContent(credentialsId: 'k8s', variable: 'KUBECONFIG_CONFIG')]) {
            sh 'mkdir -p ~/.kube/'
            sh 'echo "$KUBECONFIG_CONFIG" > ~/.kube/config'
            sh '''
              for file in deploy/common_old/other/**; do
                envsubst '${APP_NAME},${METADATA_NAMESPACE},${FULL_IMAGE},${LIMIT_CPU},${LIMIT_MEMORY},${HOST}' < "$file" | kubectl apply -f -
              done
            '''
          }
        }
      }
    }
  }
}

这个 Jenkins 流水线的设计目的是自动化构建、测试和部署一个 Web 应用程序。以下是对每个关键部分的详细说明：

1. 环境变量（在 environment 下定义） ​

这些变量在流水线的不同阶段中都会用到：

  • HARBOR_ADDRESS：Harbor 注册表的基础地址，存储 Docker 镜像。
  • METADATA_NAMESPACE：Kubernetes 中用于存储元数据的命名空间。
  • HOST：环境的主机名，通常用于 ingress 配置。
  • APP_PATH：应用镜像在 Harbor 注册表中的路径。
  • ENV_NAME：环境名称（如：dev，prod）。
  • APP_NAME：应用名称（如：wiki-root-front）。
  • APP_NAME_SERVICE：后端服务名称（如：doc-wiki-server）。
  • GIT_URL：Git 仓库的 URL。
  • LIMIT_CPU 和 LIMIT_MEMORY：容器的资源限制（CPU 和内存）。
  • IMAGE_PATH：存储 Docker 镜像的路径。
  • FULL_IMAGE：带有标签的完整 Docker 镜像名称，包含环境名称和构建编号。

2. 代理配置 ​

流水线使用 Kubernetes 代理，并指定了一个名为 nodejs 的容器模板，容器中使用的是 Node.js 版本 14.19.0。这意味着流水线将在这个特定的容器化环境中运行。

3. 流水线阶段 ​

3.1. 阶段：CheckOut SCM ​

这个阶段从指定的 Git 仓库（由 GIT_URL 定义）检出源代码，使用的是 ID 为 'gitlab-cicd' 的凭证。检出的分支由 ${BRANCH} 确定。

3.2. 阶段：Build dist ​

这个阶段负责构建前端和后端项目：

  • npm config set registry：配置 npm 的注册表。
  • pnpm install：为 wiki-backend-front 项目安装依赖。
  • npm install：为 wiki-frontend-front 项目安装依赖。
  • pnpm run build 和 npm run build：分别构建这两个前端项目。

它会构建两个独立的项目：wiki-backend-front 和 wiki-frontend-front，并打印每个项目的输出目录（dist）。

3.3. 阶段：Build Docker and Push Combined Image ​

这个阶段的任务是：

  1. 使用 Docker 凭证登录到 Harbor 注册表。
  2. 创建一个新的目录 (combined_build) 来存储最终构建的文件。
  3. 将两个前端和后端项目的 dist 目录复制到 combined_build 目录中。
  4. 将 Dockerfile 也复制到 combined_build 目录中。
  5. 打印构建目录的内容。
  6. 使用 docker build 命令构建 Docker 镜像，HARBOR_ADDRESS 被作为构建参数传入。
  7. 将 Docker 镜像推送到 Harbor 注册表中。

3.4. 阶段：Deploy to DEV ​

这个阶段将应用部署到 Kubernetes 集群：

  1. 它从凭证中读取 Kubernetes 配置文件（KUBECONFIG_CONFIG），并将其写入到 ~/.kube/config 中。
  2. 然后，使用 kubectl 应用 Kubernetes 部署文件。envsubst 命令用来将环境变量（如 APP_NAME、METADATA_NAMESPACE、FULL_IMAGE 等）替换到部署文件中。
  3. 来自 deploy/common_old/other/** 的文件会被处理并通过 kubectl 应用到 Kubernetes 集群。

主要总结： ​

  • 检出：开始时从 Git 仓库中检出最新的代码。
  • 构建：构建前端和后端项目，并生成 dist 目录。
  • 构建 Docker 镜像和推送：将这些 dist 目录合并，并使用 Dockerfile 构建 Docker 镜像，并将其推送到 Harbor 注册表。
  • 部署：最后，将 Docker 镜像部署到 Kubernetes 集群中。

这个流水线是一个很好的例子，展示了如何从构建项目到在云原生环境（Kubernetes）中部署的整个自动化过程。
