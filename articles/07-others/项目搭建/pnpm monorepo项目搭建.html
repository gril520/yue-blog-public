2.pnpm 简介 ​

1.作用 ​

节省磁盘空间

当使用 npm 时，如果你有 100 个项目，并且所有项目都有一个相同的依赖包，那么， 你在硬盘上就需要保存 100 份该相同依赖包的副本。然而，如果是使用 pnpm，依赖包将被 存放在一个统一的位置，因此：

  1. 如果你对同一依赖包需要使用不同的版本，则仅有 版本之间不同的文件会被存储起来。例如，如果某个依赖包包含 100 个文件，其发布了一个新 版本，并且新版本中只有一个文件有修改，则 pnpm update 只需要添加一个 新文件到存储中，而不会因为一个文件的修改而保存依赖包的 所有文件。
  2. 所有文件都保存在硬盘上的统一的位置。当安装软件包时， 其包含的所有文件都会硬链接自此位置，而不会占用 额外的硬盘空间。这让你可以在项目之间方便地共享相同版本的 依赖包。

最终结果就是以项目和依赖包的比例来看，你节省了大量的硬盘空间， 并且安装速度也大大提高了！

提升安装速度

pnpm 分三个阶段进行安装： 依赖关系解析。所有必需的依赖项都会被识别并提取到存储中。 目录结构计算。node_modules 目录结构是根据依赖关系计算的。 链接依赖项。所有剩余的依赖项都会从存储中提取并硬链接到 node_modules。

Creating a non-flat node_modules directory

当使用 npm 或 Yarn Classic 安装依赖包时，所有软件包都将被提升到 node_modules 的 根目录下。其结果是，源码可以访问 本不属于当前项目所设定的依赖包。

默认情况下，pnpm 则是通过使用符号链接的方式仅将项目的直接依赖项添加到 node_modules 的根目录下。

3.配置 ​

pnpm-workspace.yaml 定义工作区的根，并使您能够从工作区中包括/排除目录。默认情况下，包括所有子目录的所有包。

yaml
packages:
  # all packages in direct subdirs of packages/
  - 'packages/*'
  # all packages in subdirs of components/
  - 'components/**'
  # exclude packages that are inside test directories
  - '!**/test/**'

.pnpm-workspace.yaml 文件通常用于配置 pnpm 工作区（workspace）的相关设置，其中包括指定工作区中的包和定义哪些包的依赖项不应该被 hoist（提升）。

下面是一个示例 .pnpm-workspace.yaml 文件的结构：

yaml
packages:
  # 工作区中的包列表，列出每个包的路径
  - 'package1'
  - 'package2'
  - 'package3'
  # 更多包...

nohoist:
  # 指定哪些包的依赖项不应该被 hoist
  - 'package1/**'
  - 'package2/**'
  # 更多包...

解释：

  • packages: 这部分包含了工作区中的包列表，每个包对应一个路径。这些路径可以是相对于工作区根目录的相对路径，或者是绝对路径。列出这些包有助于 pnpm 在执行命令时正确地处理工作区中的依赖关系。
  • nohoist: 这部分指定了哪些包的依赖项不应该被 hoist。Hoisting 是 pnpm 用于优化依赖项结构的一种方式，它将共享的依赖项提升到更高层级的节点，以减少重复。但是，有时候某些依赖项可能不支持被 hoist，或者因为 hoist 导致的依赖版本冲突问题。在这种情况下，使用 nohoist 配置可以阻止特定包的依赖项被 hoist。在配置中，每个包的路径都被列出，并且通配符 ** 表示其所有子目录。

通过配置 .pnpm-workspace.yaml 文件，你可以更精细地控制 pnpm 工作区的行为，以满足项目的特定需求和依赖关系管理。

与 Vue CLI 的区别

Vue CLI 基于 webpack，而 create-Vue 则基于 Vite。Vite 开箱即用地支持 Vue CLI 项目中的大多数配置约定，并且由于其极快的启动和热模块更换速度，提供了明显更好的开发体验。在这里了解更多关于我们为什么推荐 Vite 而不是 webpack 的信息。

与 Vue CLI 不同，create Vue 本身只是一个脚手架工具：它根据您选择的功能创建一个预先配置的项目，并将其余部分委托给 Vite。以这种方式构建的项目可以直接利用与 Rollup 兼容的 Vite 插件生态系统。

4.创建 vite 子项目 ​

https://vitejs.dev/guide/

在浏览器中提供 ES 模块之前，开发人员没有以模块化方式编写 JavaScript 的原生机制。这就是为什么我们都熟悉“捆绑”的概念：使用工具抓取、处理我们的源模块并将其连接到可以在浏览器中运行的文件中。

随着时间的推移，我们看到了 webpack、Rollup 和 Parcel 等工具，它们极大地改善了前端开发人员的开发体验。

然而，随着我们构建越来越多雄心勃勃的应用程序，我们处理的 JavaScript 数量也在急剧增加。包含数千个模块的大型项目并不罕见。我们开始遇到基于 JavaScript 的工具的性能瓶颈：启动开发服务器通常需要不合理的长时间等待（有时长达几分钟！），即使使用热模块替换（HMR），文件编辑也可能需要几秒钟才能反映在浏览器中。缓慢的反馈循环会极大地影响开发人员的工作效率和幸福感。

Vite 旨在通过利用生态系统中的新进展来解决这些问题：浏览器中原生 ES 模块的可用性，以及以编译为原生语言编写的 JavaScript 工具的兴起。

vue   <script setup>和<script>区别

<script setup> 是 Vue 3.2.0+ 版本引入的语法糖，旨在简化组件的写法。相比于传统的 <script> 语法，<script setup> 提供了更简洁的写法，并且在某些情况下可以更好地推断类型。


下面是 `<script setup>` 和传统 `<script>` 的一些区别：

### `<script setup>` 示例：

import { ref } from 'vue';

export default {
  setup() {
    const message = ref('Hello, Vue 3.2!');
    const showMessage = () => alert(message.value);

    return { message, showMessage };
  },
};
</script>

<template>
  <button @click="showMessage">Show Message</button>
</template>

区别： ​

  1. 更短的语法： <script setup> 可以将 setup 函数中的逻辑直接放在 <script setup> 内，避免了重复的 setup 函数和 return 语句。
  2. 自动注入： <script setup> 可以自动将组件的 props 注入，无需手动声明。在传统 <script> 中，需要使用 props 参数并手动解构。
  3. 声明式 API： <script setup> 提供了声明式的 API，例如 ref、reactive、computed 等，可以直接使用，而不需要导入。
  4. 类型推断： <script setup> 可以更好地推断出变量的类型，无需手动添加类型声明。

使用 <script setup> 可以使代码更为简洁，并且有助于提高开发效率。
