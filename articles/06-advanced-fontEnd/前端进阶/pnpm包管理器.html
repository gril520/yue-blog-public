pnpm包管理器 ​

在使用 pnpm workspace（工作区）管理前端项目时，关于子包（workspace packages）的依赖是否应该剔除（即不显式安装到子包的 node_modules 中，而是从根目录或其它 workspace 包中复用），是一个常见的架构问题。下面针对你的四个问题逐一详细解答：

1. 子包依赖为啥要剔除？ ​

目的：避免重复、提升性能、统一版本、减少体积

  • 避免重复安装相同依赖 pnpm 默认采用 symlink + hardlink 的方式共享依赖。如果多个子包依赖同一个库（如 lodash），pnpm 会在 .pnpm 虚拟存储中只存一份，通过符号链接引用。但如果每个子包都显式声明了相同的依赖，可能会导致：
    • 构建工具（如 Webpack、Vite）误认为是不同模块（路径不同）
    • 增加 bundle 体积（tree-shaking 失效）
    • 版本冲突（比如 A 包用 v1，B 包用 v2）
  • 统一依赖版本 在 monorepo 中，通常希望所有子包使用一致的依赖版本（尤其是 React、Vue 等核心库）。通过将公共依赖提升到根 package.json 或由某个共享包提供，可以强制统一。
  • 符合“单一职责”原则 如果某个子包只是逻辑模块（如 utils、components），它不应关心底层运行时依赖（如 React），而应由最终应用（如 web-app）提供。这种模式称为 peer dependency 模式。

2. 哪些情况子包的依赖不用剔除？ ​

以下情况应保留子包自己的依赖（即不剔除）：

场景说明
开发工具类依赖如 typescript、eslint、prettier、vitest、@types/* 等。这些通常只在子包本地使用，不影响运行时，且各子包可能需要不同版本。✅ 放 devDependencies
独立构建/打包工具如子包是一个可独立构建的库（如用 rollup 或 vite build --lib 打包），则需保留 rollup、vite 等作为 devDependencies。
纯逻辑运行时依赖（无资源、无副作用）如子包封装了 axios、lodash、date-fns 等纯 JS 工具库，且希望对外暴露完整功能（无需使用者额外安装），可保留在 dependencies。⚠️ 但若主项目也用，建议统一版本。
CLI 或可执行工具包如 my-cli，必须自带所有运行时依赖（包括 commander、fs-extra 等），否则无法独立运行。
计划发布到 npm 的包必须在 dependencies 中完整声明所有运行时依赖，因为外部用户无法访问你的 workspace 结构。
包含资源/样式的 UI 组件库（特殊情况）❗ 如果该 UI 库仅在本 monorepo 内部使用，且主项目已统一安装其依赖，则子包应使用 peerDependencies 而非 dependencies； 但如果它要独立发布或自包含，则仍需保留 dependencies。

🔑 关键判断标准（升级版）：

  1. 是否会被外部消费者（npm 用户）直接使用？ → 必须保留。
  2. 是否包含 CSS、图片、Worker、动态 import、相对路径资源？ → 若在 monorepo 内部使用，优先由主项目安装，子包用 peerDependencies。
  3. 是否是纯逻辑、无副作用的 JS 模块？ → 可安全保留在子包。

3. 如何剔除子包依赖？ ​

有几种方式实现“剔除”：

方法一：使用 peerDependencies ​

将依赖从 dependencies 移到 peerDependencies，表示“由使用者提供”。

json
// packages/ui/package.json
{
  "name": "@myorg/ui",
  "peerDependencies": {
    "react": "^18.0.0",
    "react-dom": "^18.0.0"
  }
}

方法二：使用 devDependencies（仅开发时需要） ​

如果依赖只用于开发（如测试、构建），放 devDependencies 即可。

方法三：利用 pnpm 的 public-hoist-pattern（谨慎使用） ​

在根目录 .npmrc 中配置：

如果子包 A 依赖子包 B，应使用：

4. 不剔除子包依赖可以吗？ ​

技术上可以，但可能带来问题：

风险说明
多版本共存如果子包 A 和 B 各自安装了不同版本的 react，可能导致 React Context 失效、Hooks 报错等。
bundle 体积膨胀打包工具可能无法去重，导致最终产物包含多个相同库。
类型冲突TypeScript 可能因多个 @types/react 版本报错。
违背 monorepo 设计初衷monorepo 的优势之一就是统一依赖管理，各自为政就失去了意义。

例外情况： 如果子包是完全独立的项目（比如一个 Next.js 应用 + 一个 NestJS 后端），它们可以各自管理依赖，无需剔除。

总结建议 ​

场景是否剔除推荐做法
UI 组件库剔除使用 peerDependencies 声明 React/Vue
工具函数库剔除若无运行时依赖，可无 dependencies
应用入口（如 web-app）❌ 不剔除完整声明所有运行时依赖
可发布 npm 包❌ 不剔除必须包含完整 dependencies
开发工具（lint/test）❌ 不剔除放 devDependencies

合理使用 peerDependencies + workspace: 协议，是 pnpm monorepo 最佳实践的核心。

如有具体项目结构，可进一步分析优化方案。

pnpm子包打包问题 ​

你提出的问题非常典型，尤其是在 pnpm workspace + Vue monorepo 架构中使用第三方 UI 库（如 vue-pdf-sign）时。我们来聚焦分析你遇到的现象：

子包 B 自己安装了 vue-pdf-sign，主项目 A 没有重复安装；打包后功能异常；但直接运行子包 B 的入口文件（如 packages/B/index.js）却正常；最终把依赖移到主项目 A 后才正常。

这背后的核心原因，极大概率是：模块解析路径 + 资源引用路径 + 打包工具（Vite/Webpack）对 node_modules 的处理策略不一致，尤其在 pnpm 的 symlink 结构下被放大。

一、根本原因：模块解析与资源加载路径错乱 ​

1. pnpm 的依赖结构特殊性 ​

pnpm 不像 npm/yarn 那样“扁平化”安装依赖，而是采用 严格隔离 + symlink 虚拟目录 的方式：

node_modules
├── .pnpm
│   ├── vue-pdf-sign@x.x.x
│   │   └── node_modules
│   │       ├── vue-pdf-sign → (真实代码)
│   │       └── some-dep → symlink to .pnpm/some-dep@...
│   └── your-subpackage@1.0.0
│       └── node_modules
│           └── vue-pdf-sign → symlink to ../vue-pdf-sign@x.x.x/node_modules/vue-pdf-sign
└── your-subpackage → symlink to packages/B

二、为什么“子包单独运行正常，主包调用就出问题”？ ​

场景模块解析上下文资源路径基准
直接运行子包 B以 packages/B 为 root所有相对路径基于 B 的目录，能正确找到 node_modules/vue-pdf-sign/...
主项目 A 引用 B以项目根目录（A）为 root打包工具从 A 出发找资源，但 vue-pdf-sign 的资源不在 A 的 node_modules 下（而在 .pnpm/...），且路径引用是相对的 → 404 或模块 not found

关键点：打包工具（Vite/Webpack）的资源解析上下文变了，而 vue-pdf-sign 没有做“路径无关”的设计。

  • 即使 vue-pdf-sign 内部用了 ./fonts/xxx，也能基于这个“可见路径”正确解析；
  • 子包 B 通过 workspace:* 引用时，也会复用这个“顶层安装”的版本，路径一致。

本质：让第三方库的物理路径对打包工具“可见”且“稳定”。

理想情况：vue-pdf-sign 应该：

总结 ​

问题根源说明
pnpm symlink 结构导致传统相对路径引用失效
第三方库路径硬编码vue-pdf-sign 假设自己在扁平 node_modules 中

从代码可以看出，这个库（或其 fork 版本 pdfjs-dist-sign）存在典型的 路径强依赖 + Webpack 特定语法 + 动态资源加载 问题，在 pnpm workspace + 非 Webpack 打包器（如 Vite） 环境下极易崩溃。

核心问题分析（逐行拆解） ​

1. <style src="./annotationLayer.css"></style> ​

  • 这是 Vue 单文件组件（SFC）的写法，但注意：它依赖打包工具正确解析相对路径。
  • 在 pnpm workspace 中，如果该组件来自子包 B，而主项目 A 打包：
    • 实际 CSS 路径可能是： node_modules/.pnpm/vue-sign-pdf@x.x.x/node_modules/vue-sign-pdf/annotationLayer.css
    • 但打包工具（如 Vite）可能尝试从 主项目根目录 或 子包 B 目录 加载，导致 404。

风险点：CSS 资源路径断裂 → 样式丢失或加载失败。

2. require('pdfjs-dist-sign/es5/build/pdf.js') ​

  • 使用 CommonJS require，假设 pdfjs-dist-sign 安装在当前包的 node_modules 下。

  • 在 pnpm 中，若只在子包 B 安装：

    • 路径为：packages/B/node_modules/pdfjs-dist-sign/...（实际是 symlink 到 .pnpm/...）

  • 主项目 A 打包时，Vite 的模块解析器

    默认不会深入子包的 node_modules

    （出于安全和性能），导致：

    Module not found: pdfjs-dist-sign

风险点：模块解析失败 → 运行时报错 Cannot find module 'pdfjs-dist-sign'

3. require('worker-loader!pdfjs-dist-sign/.../pdf.worker.js') ​

这是最致命的问题！

❌ 问题一：Webpack 特有语法 ​

js
require('worker-loader!...')
1

  • worker-loader! 是 Webpack 的 inline loader 语法，Vite / Rollup 完全不识别！

  • 在 Vite 项目中，这行会直接报错：

    Unknown file extension "!" 或 Failed to resolve import "worker-loader!..."

❌ 问题二：硬编码 worker 路径 ​

即使你用 Webpack，路径 pdfjs-dist-sign/es5/build/pdf.worker.js 也依赖该包在 node_modules 的扁平位置。在 pnpm 嵌套结构中，这个路径可能无法被 worker-loader 正确解析。

风险点：构建失败 或 Worker 无法加载 → PDF 渲染卡死/白屏

  • Vite 无法处理这种动态 inline loader

  2. Vite/Webpack 能直接通过 node_modules/vue-sign-pdf/... 访问资源

  3. 虽然 worker-loader! 仍是 Webpack 语法，但如果你用的是 Vue CLI（基于 Webpack），它能识别

  4. 所有相对路径（CSS、worker、cmaps）都基于“顶层可见路径”，不再断裂

本质：让所有资源对打包工具“可见”且“路径可预测”

结论 ​

你遇到的问题根本原因是：

vue-sign-pdf 重度依赖 Webpack 特有语法（worker-loader!, buffer-loader!）和扁平 node_modules 结构，在 pnpm workspace + 非 Webpack 打包器环境下，资源路径和模块解析全部失效。

解决方案优先级：

  1. 主项目安装依赖（快速修复，推荐内部项目）
  2. 迁移到 Webpack 构建（如 Vue CLI，避免 Vite）
  3. 重写/替换该库（长期维护性最佳）

如果该项目必须用 Vite，且不能改主项目依赖结构，那么几乎必须 fork 并重写 vue-sign-pdf 的资源加载逻辑。

子项目安装 vs 主项目安装 ​

你这个问题非常关键，也是很多使用 pnpm + monorepo（workspace） 的开发者容易混淆的地方。我们来用最清晰、最直观的方式，对比“子项目安装” vs “主项目安装” vue-sign-pdf 的区别，并解释为什么功能表现会不同。

  • pnpm 在全局虚拟存储 .pnpm 中安装包
  • 在 packages/ui/node_modules 创建 symlink 指向 .pnpm/vue-sign-pdf@...

Webpack 打包时如何查找模块？ ​

  1. packages/ui/node_modules/pdfjs-dist-sign → ❌（pnpm 不在这里放真实文件，只有 symlink 到 .pnpm/...）
  2. my-project/node_modules/pdfjs-dist-sign → ❌（主项目没装）
  3. 继续往上…直到失败

💥 结果：Module not found

即使 Webpack 支持 symlink，它默认不会深入 .pnpm 这种非标准结构，尤其当路径是动态拼接或通过 loader 引用时。

更隐蔽的问题：资源路径上下文错乱 ​

  • vue-sign-pdf 内部引用 ./annotationLayer.css
  • Webpack 认为这个 CSS 应该在 主项目上下文 下找
  • 但实际文件在 packages/ui/node_modules/.pnpm/.../vue-sign-pdf/annotationLayer.css
  • 路径断裂 → 样式丢失

对比总结表 ​

对比项子项目 B 安装主项目 A 安装
依赖位置packages/ui/node_modules（symlink）apps/web/node_modules（symlink）
Webpack 能否找到？❌ 默认找不到（不在标准查找路径）✅ 能找到（在主项目 node_modules）
CSS/资源路径是否正确？❌ 上下文错乱，可能 404✅ 路径稳定，可解析
worker / cmaps 能加载吗？❌ 路径断裂或模块未找到✅ 正常
是否符合 monorepo 最佳实践？⚠️ 仅适用于纯逻辑库✅ 适用于含资源/UI 的库
是否会导致重复安装？如果主项目也装 → 可能多版本统一版本，避免冲突

关键理解：Webpack 的模块解析起点是“主项目” ​

无论你的组件来自哪个子包，最终打包是由主项目 A 的 Webpack 配置驱动的。 Webpack 只关心主项目及其祖先目录下的 node_modules，不自动“进入”子包的 node_modules。

所以：

  • 子包可以有自己的 devDependencies（如 eslint、vitest）
  • 但 运行时依赖（尤其是带资源、CSS、worker 的 UI 库）必须让主项目“看得见”

最佳实践建议 ​

子包类型依赖安装位置
纯工具函数库（无 UI、无资源）✅ 子包自己安装
Vue 组件库 / UI 库（含 CSS、图片、worker）❌ 不要只在子包安装 → 主项目必须安装
可独立发布的 npm 包子包安装 + 声明完整 dependencies
内部共享组件（仅本 monorepo 用）主项目安装 + 子包用 peerDependencies

一句话总结 ​

“子项目安装” = 只有子项目自己知道这个包； “主项目安装” = 整个应用（包括 Webpack）都知道这个包在哪。”

而 vue-sign-pdf 这类库，需要整个应用的打包系统都能正确找到它的 JS、CSS、Worker、字体等资源，所以必须由主项目安装。

如果你还是不确定某个依赖该放哪，可以用这个判断标准：

如果这个包会被 Webpack/Vite 打包进最终产物（.js/.css 文件），就放在主项目； 如果只是开发时用（如测试、构建），可以放子项目。

子项目安装和主项目安装判断 ​

正确认知：不是所有运行时依赖都必须装在主项目 ​

只有那些「路径敏感」或「资源敏感」的运行时依赖，才需要主项目安装。纯逻辑、无副作用、无资源引用的运行时依赖，完全可以留在子项目。

判断标准升级版（更精准） ​

当你面对一个运行时依赖，问自己：

问题如果答案是 YES → 建议主项目安装
1. 它是否包含 .css / .scss / .less 文件？✅
2. 它是否引用图片、字体、音视频等静态资源？✅
3. 它是否使用 Web Worker（.worker.js）？✅
4. 它是否通过 import('./xxx') 或 require('./xxx') 动态加载自身内部文件？✅
5. 它是否使用相对路径（如 ./utils）且这些文件会被外部调用？✅
6. 它是否是一个 UI 组件库（Vue/React 组件）？✅（通常伴随样式和资源）
7. 它是否依赖全局单例（如 Vue、React）？✅（应通过 peerDependencies + 主项目提供）

只要有一个 YES，就建议由主项目安装（或至少确保主项目能解析其完整路径）

否则（全是 NO）→ 可以安全留在子项目

总结 ​

你最初的直觉是对的：

“有些运行时依赖确实可以只在子项目安装，没必要全塞主项目。”

关键在于区分：

  • 纯逻辑库 → 子项目安装
  • 资源/路径/副作用敏感库 → 主项目安装

这种精细化管理，才是成熟 monorepo 项目的标志。

继续按这个思路设计，你的项目会既解耦清晰，又构建稳定
