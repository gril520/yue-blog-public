前端工程02： vue.config.js ​

vue.config.js 是 Vue CLI 项目中的一个可选配置文件，用于对基于 Vue CLI 创建的项目的构建、开发服务器、打包等行为进行自定义配置。它在项目根目录下（与 package.json 同级），如果不存在，Vue CLI 会使用默认配置。

主要作用 ​

1. 修改 Webpack 配置 ​

虽然 Vue CLI 封装了 Webpack，但你可以通过 vue.config.js 对其进行扩展或覆盖，比如：

  • 添加新的 loader 或 plugin
  • 修改已有规则（如处理图片、字体等资源）
  • 调整输出路径或 chunk 名称
js
module.exports = {
  configureWebpack: {
    // 直接合并到最终的 webpack 配置中
    plugins: [...]
  },
  chainWebpack: config => {
    // 使用 webpack-chain 进行更细粒度的控制
    config.module.rule('svg').uses.clear();
  }
}

  • outputDir：指定打包后的输出目录（默认 dist）
  • publicPath：部署应用包时的基本 URL（影响静态资源路径）
js

  outputDir: 'my-dist',
  publicPath: process.env.NODE_ENV === 'production' ? '/my-app/' : '/'
}

4. 环境变量与模式（mode）相关配置 ​

虽然环境变量主要通过 .env 文件管理，但 vue.config.js 可以根据 process.env.NODE_ENV 或自定义模式做不同配置。

5. 关闭/开启特定功能 ​

  • 关闭 source map：productionSourceMap: false
  • 关闭 eslint：lintOnSave: false
  • 自定义 HTML 模板：pages 选项（多页应用）

6. 多页应用（Multi-page Application）配置 ​

通过 pages 字段支持多个入口和 HTML 模板。

js
module.exports = {
  pages: {
    index: { /* ... */ },
    admin: { /* ... */ }
  }
}

注意事项： ​

  • 文件必须导出一个对象或函数（推荐对象）。
  • 修改后需重启开发服务器（npm run serve）才能生效。
  • Vue 3 + Vite 项目不使用 vue.config.js，而是用 vite.config.js。

总结： ​

vue.config.js 是 Vue CLI 项目中用于自定义构建和开发行为的核心配置文件，让你在不 eject（暴露内部配置）的情况下灵活控制项目构建流程。

Vue CLI 项目中 vue.config.js 配置详解 ​

一、整体目标 ​

你的项目是一个企业级 Vue 2 应用，支持多种部署模式（集团统一部署、独立部署、带单点登录），并依赖多个内部私有组件库。配置的核心目的是：

  • 减小打包体积
  • 提升加载性能
  • 支持多环境灵活部署
  • 提高开发效率和可维护性
  • 兼容嵌入式使用场景（如微前端）

所有配置均基于 Vue CLI 提供的扩展机制，未破坏其默认构建流程。

二、逐项配置说明 ​

1. 基础路径与构建输出 ​

js
publicPath: '/'
outputDir: 'dist'
assetsDir: 'static'
1
2
3
  • 作用：定义静态资源的基础路径、构建输出目录及资源子目录。
  • 为什么这样设：
    • publicPath: '/' 表示应用部署在域名根路径下（如 https://example.com/）。
    • assetsDir: 'static' 将 JS、CSS、图片等统一放入 dist/static/，便于运维管理。
  • 是否必要：建议显式设置，避免因默认行为导致部署问题。

2. 生产环境优化开关 ​

js
productionSourceMap: false
lintOnSave: false
1
2
  • productionSourceMap: false
    • 禁止生成 source map 文件，提升构建速度，防止源码泄露。
    • 必要性：生产环境强烈建议关闭。
  • lintOnSave: false
    • 关闭保存时的 ESLint 检查，兼容低代码工具生成的非标准格式代码。
    • 必要性：按需关闭；若团队代码规范严格，可保留。

3. 开发服务器代理 ​

js
devServer: IS_PROD ? {} : require('./proxy-table.js').devServer
1
  • 作用：本地开发时将 API 请求代理到后端服务，解决跨域问题。
  • 是否必要：开发阶段必需。

  • 作用：告诉 Webpack 这些库不打包进 bundle，而是从全局变量获取。
  • 配合 CDN 使用：HTML 中通过 <script> 引入这些库，利用浏览器缓存。
  • 效果：显著减小主包体积，加快首次加载。
  • 是否必要：当你使用 CDN 加载这些库时，此项必须配置，否则会重复打包。

5.CDN 加载的包是如何“挂载”到项目中的？ ​

这些脚本如何“挂载”为全局变量？

关键在于 这些库的 UMD 构建版本会在浏览器中自动注册全局变量：

一、为什么从 CDN 加载后就不需要打包？ ​

Webpack 在构建时会分析你的代码中所有的 import 或 require 语句。

例如：

js
import Vue from 'vue'
import axios from 'axios'
1
2

默认情况下，Webpack 会把 node_modules/vue 和 node_modules/axios 的代码 打包进你的 bundle.js 中。

但当你在 vue.config.js 中配置了：

js
externals: {
  vue: 'Vue',
  axios: 'axios'
}
1
2
3
4

这就告诉 Webpack：

“当遇到 import Vue from 'vue' 时，不要去打包 node_modules 里的 vue，而是假设运行时环境中已经存在一个全局变量叫 Vue，直接用它。”

因此，这些库 不会被打入最终的 JS 文件，从而显著减小包体积。

二、CDN 加载的包是如何“挂载”到项目中的？ ​

答案是：通过 HTML 模板中的 <script> 标签手动引入，并依赖其暴露的全局变量。

1. CDN 脚本加载方式 ​

在你的项目中，HTML 模板（通常是 public/index.html）会被 html-webpack-plugin 动态注入资源。

你在 chainWebpack 中这样配置：

js
config.plugin('html').tap(args => {
  args[0].cdn = staticCdns.production // 或 development / local
  return args
})

三、完整流程总结 ​

  1. 构建阶段（Webpack 打包）
    • 遇到 import Vue from 'vue'
    • 查看 externals 配置，发现 'vue' 对应全局变量 'Vue'
    • 不打包 vue 源码，改为引用 Vue（即 window.Vue）
  2. 运行阶段（浏览器加载）
    • 浏览器先加载 HTML
    • 执行 <script src=".../vue.min.js"> → 创建 window.Vue
    • 再执行你的业务 JS（如 app.js）→ 里面直接使用 Vue 变量
    • 因为 window.Vue 已存在，一切正常

四、注意事项 ​

  1. CDN 脚本必须在你的业务 JS 之前加载

    • 否则 window.Vue 还未定义，会报错 Vue is not defined
    • 你的 HTML 模板中 CDN 脚本写在 <div id="app"> 之后、业务 JS 之前，这是正确的

  2. 全局变量名必须严格匹配

    • Element UI 的全局变量是 ELEMENT，不是 ElementUI，这点容易出错

    • 可打开 CDN 链接查看源码末尾是否有类似：

      js
      if (typeof window !== 'undefined' && window.Vue) {
  window.Vue.use(Element);
}
// 并暴露 window.ELEMENT = Element;
      1
      2
      3
      4

  3. 仅适用于不被 tree-shaking 的库

    • 像 lodash 这种支持按需引入的库，不适合整体 externals
    • 但 Vue、Axios、ElementUI 这类通常全量使用，适合 externals + CDN

  4. 开发环境也需提供全局变量

    • 你的 staticCdns.development 使用了非压缩版 CDN（如 vue.js 而非 vue.min.js）
    • 同样会创建 window.Vue，所以开发时也能正常运行

五、是否真的“不需要打包”？ ​

准确地说：你的业务 bundle 中不包含这些库的代码，但它们仍以 script 形式参与运行。

  • ✅ 优点：bundle 小、可共享缓存（多个项目共用同一个 CDN 的 vue.js）
  • ⚠️ 缺点：增加 HTTP 请求数；依赖网络可用性；需确保版本一致性

因此，这种方案适用于：

  • 内部系统（CDN 稳定可靠）
  • 多个项目共用同一套基础库
  • 对首屏性能要求高，且用户可能已缓存过这些公共库

总结一句话：

通过 externals 告诉 Webpack “这些依赖我外面自己提供”，再通过 HTML 中的 <script> 从 CDN 引入并暴露全局变量，从而避免重复打包，实现体积优化和缓存复用。

必须配置（保障基本功能与安全） ​

  • externals（当你使用 CDN 时）

强烈推荐（性能与体验优化） ​

  • 自定义 config block loader（低代码平台）

以下是对你的 configureWebpack 和 chainWebpack 配置的 逐行、无图标、纯文字详解，解释每一部分的作用和设计意图。目标是让你彻底明白：这些代码到底在做什么？为什么要这样写？

一、总体结构说明 ​

Vue CLI 允许你通过两个方式扩展 Webpack 配置：

  • configureWebpack: 接收一个对象或函数，用于合并或修改最终的 Webpack 配置对象
  • chainWebpack: 接收一个函数，使用 webpack-chain 的链式 API 对配置进行精细控制

两者可以共存，分工如下：

  • configureWebpack：适合添加插件、设置 output、externals 等顶层配置
  • chainWebpack：适合删除/修改已有规则（如移除 prefetch）、调整 loader、设置 alias

作用：生产环境代码分包策略（核心优化） ​

1. splitChunks ​

把代码拆成多个文件，实现长期缓存：

  • vendors: 所有 node_modules 中的代码 → 单独打包
    • 名字：chunk-vendors.js
    • 特点：第三方库很少变，浏览器可长期缓存
  • common: 至少被 3 个地方引用的代码 → 提取复用
  • components: src/components 下的组件，若被多次引用也提取

✅ 目的：哪怕你改了一行业务代码，只要 vendor 没变，用户就无需重新下载

2. runtimeChunk('single') ​

  • 把 Webpack 自己的运行时代码（如模块加载器）单独拆出
  • 防止因为业务代码变更导致 chunk-vendors.js 的 hash 改变
  • 保证 vendor 缓存真正稳定

✅ 和 splitChunks 搭配使用，是现代前端性能优化的标准做法

四、总结：这套配置的整体思路 ​

目标实现手段
减小包体积externals + CDN、Gzip 压缩、Terser 移除 console
提升加载速度分包 + 长期缓存、SVG 内联、关闭 prefetch
支持多环境部署动态 CDN 注入、UMD 输出
提高开发效率自动路由、config block、alias
保障生产安全关闭 sourceMap、移除调试代码

五、是否合理？有没有风险？ ​

✅ 整体非常合理，是一套成熟的企业级工程化方案。

⚠️ 注意事项：

  1. 确保 CDN 上的资源可用且版本一致
  2. 确保 HTML 中 CDN 脚本在业务 JS 之前加载
  3. externals 中的变量名必须与库暴露的全局变量完全匹配（如 ELEMENT）
  4. 不要随意覆盖默认 rules，只做增强

你现在看到的每一行代码，都不是“随便写的”，而是为了解决某个具体问题而存在的。理解它们背后的“为什么”，比记住“怎么写”更重要。
